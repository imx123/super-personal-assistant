# Phase 1 改造计划 V2

本版以《要求.md》、架构交接稿及本轮用户纠正为准，替代旧 M1 方案。开发基线固定为上游 `8c32a9dc5d72c033816c6a8110b37f40cf94fba4`。旧 Windows 预览和实测记录保留，供对照。新的开发与验收先建立独立 Windows DSH 运行时，再在其中安装原版及改造版。

## 需要纠正的改造

旧版把本地入口放在 Superagent 管理面板，另用句首规则决定是否建单，同时将原主 Session 改成通知查看器，并屏蔽 Worker 的原有工作工具。这改变了上游任务的入口、判断者和执行能力。实测三条正常表达全部停在待处理，且没有下一步。规则命中的对照只证明了建单、派工和停止链路在受限模式下可运行。

旧 Windows 预览使用独立的 `DSH_HOME` 和数据库，启动时仍调用现有 DSH 安装的 CLI 和宿主。因而预览仍与现有安装共享宿主版本和内置 bundle。工具权限只决定 Agent 能做什么，解决不了宿主版本、依赖和安装位置的冲突。

V2 以原版 **主 Session 聊天框**作为唯一新增能力所使用的本地任务入口。用户在这个既有窗口下指令、收到回执和 Report。Superagent 侧栏继续用于看状态、找 Worker、看派工历史和执行控制。

```text
原版主 Session 聊天框
  → 本机用户消息接入 Trigger
  → 原版 Policy 与主 Session 路由工具
  → 原版 Engine 创建 Ticket 和 Assignment
  → 原版 DSH Worker 在独立会话中执行
  → 用户直接插话或执行控制
  → Report 或执行状态事件回到原版主 Session
```

## 保留和调整的边界

| 模块 | V2 处理 |
| --- | --- |
| 主 Session | 保留原版 Router 身份、系统提示和 `orchestrator_route`、评估、查询、重试等工具。已有 GitHub 和飞书候选继续走原路径。只为本机用户来源补充必要的任务语义，个人日程、仓库调研和方案讨论均可表达为独立 Ticket。 |
| Engine、Store、Effects、Executor | 从上游版本起步，复用建单、授权、派工、执行、重试和恢复。保留 Router 对独立 Ticket 的管理关系。 |
| 权限 | 沿用上游的会话预设、工具范围、Policy、Mandate、工具守卫和审批关系。Worker 能使用其 profile 已配置且获准的文件、Shell 或网页等工具。在独立运行时内实测原版预设的行为。需要额外能力时，单独列出该能力及授权依据。 |
| 主窗口 | 继续使用原版主 Session 和 DSH composer。撤出旧版额外的「描述任务」表单及其独立收件规则。 |
| Worker 交互 | 通过原生 DSH Worker 会话查看历史和插话。复用已有 Superagent 工单详情和原生会话跳转，必要时补 Ticket、Assignment、Session 和回报之间的定位信息。 |
| Windows 部署 | 单独处理上游的路径、Git 探针及工作目录适配。优先在测试仓库和测试账号条件下跑通原版启动流程。遇到确切兼容问题时只调整对应的部署接线，保留正常权限检查。 |

旧版的 `local: true` 整体旁路、句首白名单、主 Session 工具清空、Worker 工具清空及独立面板提交 API 都退出新版验收路线。旧状态库保留原样，便于复盘。旧改造中经对照仍成立的停止语义、测试和报告证据可以逐项移植。

## 实施步骤

### M0 独立 Windows DSH 运行时

1. 在项目工作区内准备一份可并行启动的 Windows DSH 运行时，优先使用固定版本的独立 CLI、所需 Node 运行时和 Web bundle。核对上游包的版本范围、锁文件和已有基线。Debian 上跑过原版执行闭环的 `0.2.1-rc.3` 可作为首个候选，最终组合以 Windows 原版实测为准。
2. 启动命令引用独立副本的绝对路径。启动时记录实际进程可执行文件、CLI 入口、DSH 和 Node 版本、内置 bundle 解析路径以及 Superagent 包校验值，逐项核对它们来自测试副本。验收时检查 PATH 或 bundle 解析失败是否会错误地回落到现有 DSH 安装。
3. 单独设置本轮进程的 `DSH_HOME`、profile、依赖与缓存目录、临时目录、SQLite、Worker 工作区和会话持久化路径。使用独立 loopback 端口和浏览器资料。模型只注入本次授权的凭据，保持现有 DSH 的全局配置、凭据存储、插件、会话和默认模型独立。
4. 先同时观察现有安装和测试实例的身份与端口，再复测独立实例的启动和停止。比对现有安装与 profile 的关键文件状态，核实测试实例的实际读写目录。运行时、版本和数据路径全部可区分后，才进入改造。

以上是运行时与数据隔离。原版 Worker 的 Shell 和文件工具仍按宿主权限执行。测试任务只使用合成日程、独立工作区及明确获准的只读资料。如果便携 Windows 运行时无法独立加载所需组件，先报告具体依赖和缺口，再讨论独立 Windows 虚拟机等方案。

### M1 从原版建立 Windows 对照

确认固定上游源码、实际安装版本、默认主 Session 工具、Worker 预设和工具守卫。先用 M0 的独立 Windows 运行时、测试仓库和原版部署接口跑一个原版候选任务，记录从 Trigger 到 Report 的实际链路。上次在 Debian 的基线只能用作行为对照，Windows 启动和工具执行单独取证。

这一阶段输出实际的权限对照表。分别核对 Router 自有工具、Worker 自有工具、继承工具、工单权限、批准动作和真实执行目录。任何需要新增的能力都要定位到具体角色和操作。

### M2 让主 Session 原生输入参与上游路由

1. 用一条合成消息检查 DSH 原生输入事件、消息 ID、消息来源以及模型请求的实际顺序。选择能可靠区分操作者消息、Worker Report、系统注入和 Agent 自生成消息的接入点。
2. 增加窄的本机输入适配器。只有指定主 Session 中经现有 DSH 登录入口提交的用户消息才可形成此来源的 Trigger。操作者身份由服务端绑定。使用稳定消息 ID 做幂等，在重复投递、刷新或重启后仍只有一个 Trigger。
3. 让原版主 Session 得到有 `trigger_id` 的候选，复用它的 `orchestrator_route` 调用。先验明候选能在正确的模型步骤到达，再决定具体挂接方式。验收要求一条指令只做一次业务决策，Worker 通知也不会反向变成新的用户任务。
4. 主 Session 在当前对话给出真实回执，区分接收、已派工且等待启动、Worker 已开始、需要澄清。明确任务直接走上游工具，确实缺信息的请求留有可见问题和继续处理方式。复杂设想允许建一张「梳理试用场景」的独立工单，也允许按实际缺失信息追问。

架构里的 Fast Router 在此阶段是同一主 Session 的快速处理路径。Phase 1 使用已有 Ticket 的明确关联和原版路由工具。完整 High-level Router、Project Profile、PM、RAG 和远程 Node 留在后续阶段。

### M3 原生 Session 和执行能力

验证两个真实 Worker 能并行执行，各自拿到完整原始请求、任务目标和可核对的完成条件。让主 Session 用现有字段传达任务目标，Worker 执行中直接使用其原生会话输入。路由和工单页面应能说明哪个 Session 对应哪个 Assignment，以及插话何时进入 Worker 的下一步。完整对话保存在原生 Session。

Windows 的有效工具由实际 profile 和上游守卫决定。仓库调研需要一次有证据的读取。如果 bb-mcp 的权限或网络不足，使用明确获准的只读 checkout 或报告真实阻塞。仅凭仓库名称、URL 或模型生成的命令无法算作读取成功。

### M4 三种控制与结构化回传

| 操作 | 执行路径与验收 |
| --- | --- |
| 中断当前回合 | 复用 DSH 原生取消，等真实回合结束。Ticket 与 Assignment ID 保留。Router 收到带操作者和中断原因的状态通知，能区分人工中断与自然空闲。 |
| 停止本次派工 | 先验证上游接口缺口，再移植必要的事务命令。按当前 Assignment ID 停止受管执行，保留 Ticket 和会话。Router 收到明确的派工结束事件，旧 Assignment 的回调和过期停止请求受身份校验。手动重试另建 Assignment。 |
| 取消整个工单 | 复用原版 Ticket 停止和 `ticket_ended`。验证活动模型回合及本工单受管任务确实停止，工单不会被旧输入重新启动。 |

Worker 的结构化结果仍通过 `orchestrator_report` 和原版 Effects 回 Router。人工操作产生独立的状态事件，字段包括操作、操作者、Ticket ID、Assignment ID、Session ID、实际停止时间和已有产出。原版主 Session 可由消息唤醒并正确解读状态。验收同时检查通知入库、模型确实收到、主窗口正确展示。控制动作本身不会触发新的派工。

### M5 刷新、恢复和上游回归

复测同一输入重复提交、停止与完成竞争、过期 Assignment、后台任务清理、Worker 失败、主窗口刷新、宿主重启及历史保留。分别记录引擎状态和真实会话回合状态。跑上游仓库模式回归，核对旧 Source 准入、工具授权、报告和恢复行为。

## 真实场景验收

通过 Computer Use 操作原版 DSH GUI。Router 与 Worker 使用真实 DeepSeek V4.1 Flash，通过每个 Session 的模型请求头取证。保留以下原始开头，验收时禁止改成某个关键词来触发。

| 输入 | 必须观察到的结果 |
| --- | --- |
| 「我明天下午来了个紧急会议，帮我看看我的日程怎么改」加合成日程 | 由主 Session 派给 Worker。Worker 获取完整时间、不可移动事项和缓冲要求，并能给出可核对的调整建议。仅使用模拟数据。 |
| 「帮我调研一下这个 GitHub 仓库」加 bb-mcp 链接 | Worker 收到明确调研目标，通过实际可用的只读途径取得仓库证据。遇到权限问题，准确说明缺什么，阻塞返回 Router。 |
| 「我想要做一个 superagent」加高层设想 | 保留构想原文，作为独立的场景梳理任务，或先提出确实必要的澄清。需要证明可从澄清继续到派工。输入只给设想，架构图和实现方案由项目自己保留。 |

演示分两轮。第一轮让任务实际执行到可验证的结果，至少一项完成并自动回传。第二轮保留两个并行 Worker，向其中一个插话，在实际运行中操作中断、停止派工和取消工单，必要时分开重跑同一场景。确认 Router 收到准确原因并在原主窗口反馈。最后刷新并重启验证历史。记录实际工具调用、运行时间、Ticket、Assignment、Session ID、终止事件和原始 Report。只有模拟模型与规则改写样例的结果单列。

## 决策与交付

先提交本计划。实施时按「独立运行时与原版 Windows 对照 → 主入口派工 → 原生干预与回报 → 真实演示」四个检查点交付证据。预期只涉及输入适配、Windows 部署接线、已有页面的必要状态映射和最小停止命令。对任何权限或审批变化另列依据、范围和影响。
