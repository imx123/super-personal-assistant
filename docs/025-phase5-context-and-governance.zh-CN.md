## 0. 这一轮做了什么，没做什么

**做了**：

1. **有界上下文拼装**：Router 的直接用户回合、PM 的项目输入与自动交接、Worker 的启动（快路由与正常派工）都得到一段**有硬预算**的参考材料。
2. **显式稳定偏好的写后即读**：同一个 Router 会话里，人刚说的偏好在下一次直接指令中可读——它仍挂在待审队列里，没有变成任何别的会话可信的长期记忆。
3. **真实有效采用**：Worker 与 PM 的报告可以点名它真正用到的记忆；服务端只认**这一任务真正注入过**的那一部分。
4. **控制台治理**：长期记忆可以改写（新版本 + 并发校验）、置顶，以及操作员显式**永久删除**（正文、同 scope 同内容的待审副本与索引条目一并抹掉，不留指纹、不留墓碑）。**不在生效中的行也归操作员管**：待复核的与历史版本同样删得掉，列表加一个复选项才看得见它们。
5. **控制台检索的作用域筛选**：搜索条件、当前模式与结果始终属于同一个作用域。
6. **按 ID 读取**：普通 Router / PM / Worker 也能用 `control_memory_search` 读**一条**记忆（`memoryId` 与 `query` 二选一）；未知 id、已删除的 id 与无权看的 id 是**同一种**答复。
7. **拒绝审查包按原样发**：这一轮把 `denial_review` 也算作**封包**。它是**一个作用域**的事，在它后面挂一段一般上下文，就会把别的项目正在跑的工单 id 摆到读它的人面前。

**没做**（明确留给后面）：

- **没有改写历史备份**：备份是历史快照，运行库的删除不改写它（备份的物理清除是另一件事，另议）；本轮也**不做整库 VACUUM**。
- **没有跨设备实现**：这一轮仍在单 DSH 节点上运行；`node_id` / `backend_id` 的预留照旧。
- **没有改 Event History 与投递**：持久事件历史、协调投递与作用域判定不是这一轮的新功能。
- **没有新增 Agent 工具**：`P5-4` 的记忆管理员仍然**正好四个** `memory_service.*` 工具；Router / PM / Worker 的工具集一个也没多（`control_memory_search` 只是多了一个可选参数）。

## 1. 有界上下文拼装

### 1.1 一个新的模块

`src/memory/context-assembly.ts` 是**纯投影**：没有库、没有节点、没有模型。它只决定三件事。

| 决定 | 内容 |
| --- | --- |
| **顺序** | ① 精简实时状态 → ② 当前项目的手工 Project Memo → ③ 通过 `R_min` 的 Top-≤5 长期记忆 → ④ **本会话内**等待审核的显式偏好 |
| **预算** | Router 600、PM 800、Worker 500 token（`ControlPlaneOptions.contextBudgets` 可替换） |
| **栅栏** | 全部用 `src/infra/text.ts` 的 `dataFence` 写成一段 `<context_reference_data>`，正文按数据转义 |

**Token 的估算是保守的**：同时取两个读数的较大者——UTF-8 字节数 ÷ 3，以及代码点数（ASCII 以外的每个字符算 1 个 token，ASCII 每个算 ¼ 个）。这样「纸面上合预算」的块，在模型那里大概率也合预算。

**预算只管参考材料**：人的原话与任务的约束**从不被截断**。块是加在它们**旁边**的，不混进它们里面。

**围栏永远闭合**：块是用唯一那个引用数据的助手写出来的，所以恰好一个开标签、一个闭标签；围栏里的话不能关掉自己的围栏、不能开出自己的标签、也不能夹带一个换行。放不下时丢的是**条目**，不是闭标签。

### 1.2 权威身份来自哪里

拼装的每一部分都从**会话自己证明的身份**推导范围，从不从请求：

| 角色 | 实时状态 | Project Memo | 长期记忆 |
| --- | --- | --- | --- |
| Router | 它管理的池 | 无（Router 不属于任何项目） | `user_global` + 全部 `node_env` + 全部 `project` |
| PM | 它**真正被委托**的项目与节点 | 它的项目 | `user_global` + 它的节点 + 它的项目 |
| Worker | 它的 Assignment、它的工单、它的节点 | 它的工单所属项目 | `user_global` + 它的节点 + 它的工单所属项目 |

实时状态用的是 `P5-1` 的 `LiveStateService.forSession`，它自己按会话记录判范围；长期记忆用的是 `P5-5` 的检索器，它自己按调用方判作用域。**两处都不接受请求里的任何词。**

### 1.3 接在哪些路径上

**唯一的发送入口**：`ControlPlane.sendMessage`。参考材料在那里拼装一次，因此**每一条普通 `session.message` 都带着它，而且只拼一次**。

**三种封包按原样发，不加参考材料**：外部唤醒的隔离信封（`EXTERNAL_ENVELOPE_LIMIT = 4096` 字节，闭合标签必须是最后一样东西）、流转摘要（`STREAM_MESSAGE_LIMIT = 4000` 字符，`Session detail: …` 那一行必须是最后一行）与**拒绝审查包**。前两个**自含**自己的栅栏与自己的引用，加上一段参考材料就会顶破自己的预算，或者把必须留在最后的那一行挤下去。**拒绝审查包的作用域边界也是这样来的**：它自带一段有界的「这次治理的工作」投影，讲的是**一个作用域**的事；在它后面再挂一段一般上下文，就会把整个控制面的实时状态摆到读这份审查的 Session 面前——**别的项目正在跑的工单 id** 也会跟着进去。那样一来，审查就不再是那一份审查了。普通 Router 对话是**另一条路**：它照旧带参考材料。

**判定只认协调的种类，不认消息的字**：`src/control/delivery-outbox.ts` 的 `isSealedDelivery` 按**权威的投递种类**（`external_wakeup`、`stream_digest`、`denial_review`）判定；种类由**产出它的那一方**给出（投递目录按行给出，重放时也按行给出），控制面在种类缺失时按幂等键回查投递目录自己的记录。**任何时候都不解析调用方的文本**来决定能带什么。

| 路径 | 位置 | 说明 |
| --- | --- | --- |
| Router 的直接用户回合 | `ControlPlane.deliverRouterMessage` → `sendMessage` | 人的原话整段照发，参考材料加在后面 |
| 快路由交给 PM 的自动交接 | `ControlPlane.handInstructionToProjectPm` → `sendMessage` | 同上 |
| Router 交给 PM 的交接 | `ControlPlane.deliverRouterHandoff` → `sendMessage` | 交接消息与投递载荷是同一份 |
| 报告唤醒（Worker → PM） | 协调投递 → `deliverCoordinationMessage` → `sendMessage` | 唤醒**带着它那张工单与那次派工**：PM 那个回合的记忆范围因此是工单范围，不是项目范围 |
| PM 的项目报告 → Router | 同上 | 报告与外部材料仍是**被围栏的数据**，不是人的指示 |
| 外部唤醒 / 流转摘要 / 拒绝审查 | 同上 | **封包**：按原样发，参考材料一概不加 |
| 控制台直发 | `sendMessage` | 同一条路 |
| Worker 的启动（快路由与正常派工） | `ControlPlane.ensureWorker` | 快路由的 Worker 在**第一个本机回合**就看得见 |

**快路由不多花一次 Router 回合**：拼装全是程序动作（读记录、读检索、拼字符串），不调用任何模型。

**最后一次复核在真正出门之前，而且是同步的**：`sendMessage` 先拼装参考材料（拼装会等检索，可能等 embedding provider），**然后**才做最后一道闸门——当前 Session、当前**代际**、以及这次投递自己带来的那道检查（订阅是否过期、目标是否被换掉）。**最后一道检查与 `node.send` 之间没有 `await`**：会等的检查等于可能已经过期的检查。Worker 的启动同理：brief 拼好之后、create 出门之前，再读一次**当前 Assignment** 与**目标代际**。

**Worker 的上下文在 `worker.create` 之前拼好**，随 brief 一起出门；账也在 create 之前写下，所以**刚启动就回报的 Worker 不会丢**。投递在**成功确认的那条路径**上补记一次（`delivered_at`），而这次补记**就是闸门**：没送到的块不在任何人面前，账里的 id 不能被认领。回报早于 transport 回执的合法并发**不丢**——认领先记成「在途」，投递确认时自动结算；**不额外发模型回合**，也**不从模型文本里捏造确认**。回执丢了（`NodeUnconfirmedError`）**不算失败**：消息可能已经到了，这种投递不猜着重发。**节点自己说「消息在那儿」也是一次证明**（`delivery.evidence` 回答 `inbox` 或 `consumed_turn`）：这时候账照样结算，问的是节点，不是模型，也不占一次回合。

### 1.4 什么被注入过，是有账的

`memory_context_injections` 记下每次注入：Session、Assignment、Ticket、项目、机器、**代际**、**交付 id**、**块的内容快照**，以及真正在块里的记忆 id。

- **注入 id 由交付的稳定 id 派生**（`router-msg:<id>`、`fast-relay:<id>`、`router-handoff:<id>`、`worker-create:<assignment>`），**不由提问的文本 hash 派生，也不由记忆集合派生**：两次真的不同回合即使问同一句话也是两行；同一交付重试一次（回执丢了再送）仍是同一行。
- **同一交付只有一套记忆**：重试时**复用账里那份内容快照**，不重新拼装——所以账里记的和真正上线的永远是同一份，重试也不会和它重复的那次共享另一套记忆集合。
- **代际由节点信任代际与 Assignment 生命周期代际组成，不含令牌版本**：刷新令牌换的是凭据，不是这一段命；账名跟着令牌变，就会忘记自己刚写下的一行。
- **代际解析不出来就不写这一行**：空串不是一次核验。代际说这条记录属于 Session 的哪一段命。
- 认领时比对的是**整套绑定**（Session + Assignment + Ticket + 项目 + 机器 + 代际），不是只比对 Session 与 Assignment。

这张账是第 3 节「有效采用」的判据：报告点名的记忆 id 必须**在这张账里、而且那一次投递真的确认过**，否则一律不算——投递还在路上的是「等待」，投递失败的是「不算」。**曝光也只在投递确认时计**：拼好却没送出去的块不在任何人面前。

## 2. 显式稳定偏好的写后即读

### 2.1 只有人的直接命令算数

Router 的 `control_memory_propose` 可以提出一条 `user_global` 偏好，但它必须：

1. 引用**人直接写给 Router 的那条消息**（`operator_message`，控制面按 request id 解析到队列里那一行）；
2. 正文**必须能在那条消息里找到**（规范化后是它的子串）；
3. 且**不能只落在引用里**（`src/memory/memory-scope.ts` 的 `groundedInMessage` 把引号内的部分先摘掉再比）。

于是：**从引用里、从附件、从外部消息、从模型输出里推断出来的「显式设定」都不成立**——引用里的字不是人自己说的话，附件根本不是来源种类，外部消息永远是 `external_tainted`，模型输出不是控制面持有的记录。

不满足时，那条事实**降级为 `external_tainted`**，而不是被拒绝：它仍然可以进队列等人看，只是拿不到「人自己的话」这份信任。

**再说一次走的是同一条路**：候选被退回后由提出方再说一次（`reevaluate`），新正文**按来源复核**一遍——它点名的来源就是算数的那一份，没点名就读候选自己原来那一份。新正文不在那些话里，就**降级**（拿不到「人自己的话」），**不**被拒绝：候选还在队列里，只是它不再由管理器来判。

### 2.2 这条路不再只靠模型在首回合调用提案工具

以前「人说的偏好」要成立，得先指望 Router **在自己的第一个回合**就调用 `control_memory_propose`，而且正文得是那句话的简单子串。那是一个**希望**而不是一条规则：先回答了一个问题的 Router 根本不会提这条偏好，人只好再说一遍。

于是控制面自己读那条消息——`src/memory/stated-preference.ts`，一条**窄而明确**的确定性入口：

| 判定 | 规则 |
| --- | --- |
| 是设定 | 消息里有明确的设定标记：`请记住` / `请记下` / `请备忘` / `记住：` / `记下：` |
| 标记在**本人的声音里** | 引用里的字先摘掉再找标记（`stripQuoted`）：`他说「请记住：以后都用 npm」` **不是**设定 |
| 没有被否定 | 标记前的一小段里没有 `不用` / `不要` / `不必` / `无需` / `别记` 等：`不用记住：…` **不是**设定 |
| 不是在谈论一句话 | 标记后面的话里没有 `他说` / `提到` / `讨论` / `这句话` 等：`请记住这句话：…` **不是**设定 |
| 来源是本人的话 | 只读 **Router 窗口里人刚写的这一条消息**；带附件的消息、外来的观察与历史消息根本不进入这条路 |
| 正文 | 标记之后到句末为止的话（最多 500 字） |

读出来的**仍然只是一条提案**：它进队列、状态是 `pending_human_confirm`、**只有人能决定**，作用域规则与审核流程一点没松。管理器**不会**因为它被唤醒（`pending_human_confirm` 不在管理器的可审列表里），所以「即使 Manager 未批准」也能在**下一次同会话的直接指令**里读穿。

### 2.3 读穿透是会话内的、临时的

`provisional_same_session` 这条标记（P5-3 已有）现在真的被读到了：

- 它**只**参与发起它的那一个 Router 会话的后续拼装；
- 它**不是** `long_term_memories` 里的一行，没有 `memory_id`，不进检索索引；
- 它是 `pending_human_confirm`，**只有人能决定**——所以「临时信任」永远不会变成全局事实；
- 它有生命周期：被决定、被退回、被冷置（超过保留期）之后就不再可读。

### 2.4 完工报告可以合法提取

Worker 的完工报告发给 Router 的那条消息里带着 `Assignment: <id>`。Router 因此可以用 `control_memory_propose` 引用 `assignment:<id>` 提出候选——这是一条控制面**真的持有的记录**，其可信度由记录本身推导（派工结束 = `verified_execution`）。

报告消息里加的那句提示**只点名来源，不给信任**：它说「可以提一条，用上面的 Assignment 作来源」，没说这条事实可信。可信度仍然是记录推导出来的。

一次性报告和聊天不灌队列：提示里写明「最多一条」，而且只有 `ready` 的结果才带这句。

## 3. 真实有效采用

### 3.1 模型能说什么，不能说什么

Worker 的 `control_report` 与 PM 的 `control_project_report` 多了一个可选字段 `appliedMemoryIds`。它是**模型自己的说法**，不是事实。

服务端做三件事：

1. **比对**：名字里的 id 必须**在这次注入的账里**（`memory_context_injections`），而且比对的是**整套绑定**：Session、Assignment、Ticket、项目、机器、**代际**。没在账里的 id 一律不算——别的项目的记忆、一个从没给过的 id、一个凭据，都不算。**在账里还不够**：那一行的那次投递必须**真的确认过**（`delivered_at`）。投递还在路上时，认领**等待**（Worker 先回报、后回执的合法并发），投递失败时**不算**。
2. **绑定**：算数的那些被写进 `memory_applied_claims`，连同 Session、Assignment、Ticket、项目、机器、代际与作用域一起存下；等待中的那些记着**它等的那次交付**，投递确认时自动结算。
3. **记账**：等**工作真的结束**（派工结束、工单以 completed 收尾，或 PM **接受**了评审），才用 `P5-5` 的证据闸门记账。

**代际为空时不成立任何声明。** 代际说这条注入属于 Worker（或 PM）Session 的哪一段命：Worker 被换掉之后，新令牌认领不了前任的活；`generationOf` 解析失败时返回空串，而**空串不是一次核验**——这样的注入根本不写，这样的声明也不成立。**令牌刷新不影响代际**：代际说的是哪一段命，不是哪一把凭据。

### 3.2 PM 的声明绑定到一张工单，不绑定到一个项目

以前 PM 的声明按 `projectId` 记账，于是**这个项目之后每张工单的评审都会把历史声明再加分一遍**。现在：

- `control_project_report` 多了一个**可选**的 `ticketId`。后台**严格验证**它：必须是这个 PM 自己项目里的工单，而且它得有当前的 Assignment。
- **不点名工单就不记**：没有工单就没有活可绑，声明落不下去。
- 声明的证据是**那张工单**：认领与记账都按工单 + 当前 Assignment 走。于是同一张工单的一个已完成任务**最多被记一次**，项目里的**另一张票**不会把旧声明算进来，**旧一轮**的声明也不会算到新一轮的头上。
- PM 那个回合的注入是**工单范围**的（报告唤醒带着工单与派工过去），所以「上一次交接的账」不能被拿来**名义上**认领后续回合——交接的注入是项目范围，认不了工单的声明。

### 3.3 什么时候不算

| 情形 | 结果 |
| --- | --- |
| 进度报告 | 只写claim，**不**增加效用 |
| 只读工具、检索 | 只增加曝光，**不**增加效用 |
| 模型点名了一个没给过它的 id | 不算 |
| 代际对不上（Worker 被换过、节点重启过） | 不算；**令牌刷新不算**：代际说的是哪一段命，不是哪一把凭据 |
| 块拼好了却**没送出去** | 不算，**也不计曝光**：没送到的东西不在任何人面前 |
| 同一个任务重试、重启、换 Assignment | 各算各的，不串；同一交付重试**复用账里那份内容**，所以重试不会带着另一套记忆上街 |
| 记忆在注入之后被**替换**（新版取代） | 不算：只有**当前生效**的那一版能被记账 |
| PM **打回**返工 | 相反的方向：**那次派工**的声明里的记忆置信度下降一步，跌破下限的转入 `needs_reverify`；后来正常的任务继承不到这次已失效的适用声明 |
| 报告或工单**失败、超时、被搁置** | 不增加效用：只有工单以 completed 收尾或 PM **接受**了评审才记账 |

「当前生效」由记账闸门自己判：不是 `active` 的记忆不参与记账。机器范围（`node_env`）的记忆也可以被记账，但**机器以控制面自己持有的记录为准**（那次派工真正跑在哪台机器上），报告里写的机器不作数。

## 4. 控制台的治理

### 4.1 本轮裁决：永久删除，不留墓碑

用户裁决了删除语义，采用**永久删除**（不是那份「指纹抑制 + 墓碑」的基线）：

- 删除 = 正文**连同行一起消失**：同 scope、同规范化内容的待审副本、关键词索引条目、指向它的引用与声明，一并抹掉；
- **不留指纹、不留归档副本、不留墓碑**——没有一张表会记住「这条被删过」；
- 删除后按 ID 读取与未知 ID 返回**同一种**「记忆不存在或已被用户删除」；
- 同样的内容以后仍可走正常候选流程，**以新 ID 生效**：删除的是这条记忆，不是它的来源。

**模型与 API 伪装 operator 一律不行**：删除的入口只认控制台连接密钥（只读密钥 403），请求体里没有任何字段能自称 operator；权威看的是**调用方的角色**，而角色来自请求带的凭据。

**一次事务，或什么也没发生**：正文、副本、索引条目与相关引用是一件事，它们一起走或一起留。

**版本校验**：删除带上操作员读到的那一版 checksum，版本过期是 **409**。

**运行库抹掉的是它自己**：删除后的正文在 SQLite 的空闲空间里以零覆盖（core `PRAGMA secure_delete`），关键词索引自己的 `secure-delete` 选项让索引不留下旧正文。**历史备份与原始记录按各自的保留规则留存**：备份是历史快照，运行库的删除不改写它（备份的物理清除是另一件事，另议），本轮也**不做整库 VACUUM**。

### 4.2 删除抹掉的是**同一件事的全貌**

只删那一行是不够的：队列里**早就在等**的那一条候选，删掉的正是那份正文，它若还在，之后仍可以被批准，把删掉的事实原样复活。于是：

- **删除时**，同一作用域、同一规范化内容、还在队列里的候选**一并删除**（它们就是那份正文）。这次是**删除**，不是关闭。
- **删除之前**就存在的候选——包括被人**退回**之后又被**重新编辑**成同样字样的那条——随它们的正文一起消失，因此不能再被决定成记忆。
- **别的作用域、别的正文不受影响**：另一个作用域里同样的话是另一条事实，另一个作用域里同样的话也是另一条事实，都留着。
- 审核流程本身一点没松：审核流程照旧，只是被删掉的那份正文没有东西可审。

**删除与投递的竞态**：注入账里存着那一趟**真的带过**的块，所以删除要同步撤回带着已删正文的**应用自有重放快照**，并让投递中的那一趟连同它等待的声明一起作废；**已经发生的历史投递按草稿保留**（不改写已经送达的事实）。删除与发送之间那最后一步由**最靠近传输的一次同步检查**兜住：块里那条记忆若已不在，这趟消息就不带它出门。

### 4.3 改写与置顶

- **改写 = 新版本**：新行 `supersedes_id` 指向旧行，旧行转 `superseded` 并写 `deprecated_at`，两者**同事务**切换。事实的**信任不变**（改个错字不会把不可信的事实变成可信的），新版本的效用从零开始——它得重新挣。
- **并发校验**：每个动作都带上它读到的那一版（checksum）。版本变了就是 **409**，两个人不会互相覆盖。
- **版本校验涵盖治理相关的字段**：置顶、置信度、后继与未决冲突都算在版本里。所以**即使时钟不动**（测试里固定时钟、或者时钟粒度很粗），两个真的不同的版本也**不会共用一个 checksum**——置顶过的那一条与没置顶过的那一条是两条版本。
- **旧版本 / 并发更新的约定**：动作先查版本、再查状态。一个做在旧版本上的动作一律是 **409（`STALE_MEMORY`）**，无论那条记忆在这期间变成了什么状态；一个已经**被删除**的 id 则按「没有找到」回答，不告诉调用方它曾经存在。
- **置顶**：同分时排在前面，别的什么都不改。

### 4.4 界面上要说清的话

永久删除的二次确认里写明四件事：**正文与同内容的待审副本、索引条目一起消失**、**不留指纹也不留归档副本**、**旧工单会话与已有备份按各自规则保留**、**同样的事实以后仍可能从原始来源再次被提取出来**（那时它是一条新记忆）。

检索区收短了：说明只留必要的一句，**评分依据留在结果区**（每条命中带着自己的分数拆解与理由）。新增**作用域筛选**：默认是全局视野，可以按已有的项目与机器收窄；换作用域时在途的答案作废，**慢请求不会覆盖新作用域的结果**。

### 4.5 不在生效中的那些行，也归操作员管

**待复核的记忆与历史版本仍然在运行库里**：它们的正文还在文件里。以前的删除只认「生效中」的行，于是这些正文**永远删不掉**——人打开列表看得见它们，却删不掉。

- **删除不再只认生效中的行**：版本对得上（checksum 一致）的既有行都能永久删除，规则与生效中的行**完全一样**——同一作用域、同一规范化内容的副本一起走。**召回、按 id 读取与检索照旧只认生效中的行**：Agent 读不到停用的正文。
- **控制台多一个复选项**：列表默认只看生效中的记忆；打开「显示历史版本与待复核记忆」之后，历史版本与待复核的行**并排显示**，每一行都写明自己的状态，并且**照样有删除动作**。
- **编辑与置顶仍只对生效中的行可点**：停用的行不给这两个动作——改写一条已经退下的版本没有意义，置顶一条不参与召回的行也没有意义。
- **样式、原有筛选与确认文案都没动**：新增的只有一个按钮、一行状态说明和一次读取参数。

### 4.6 一个请求只能问一件事

`GET /v1/tools/memory/search` 有两种问法：给一个 `memoryId`（要那一条）或给一个 `q`（要一批）。以前这行代码先把 `memoryId` 当成必填的字串读，**没给 id 的时候直接 400**——于是普通的关键词检索自己也过不去。现在**可选参数先按原样读**：给了 id 就查那一条，只给 `q` 就检索，两个都给（问了两件不同的事）**400**，参数在那里却是空的（等于什么都没问）**400**。权限与 404 的话一个字没改。
